# Generated release scripts

The deployment wrappers around `OsmToolsBasic.jar` are **generated by Gradle**, not
kept in the repository. Everything they need — jar name, tool paths, default
directories, JVM options — is declared once in `osmToolsBasic/build.gradle`, so the
scripts stay consistent with each other and with the CLI.

---

## 1. The scripts

| Script | Gradle task | What it does |
|---|---|---|
| `update_planet_file.sh` | `createPlanetUpdateShScript` | Refresh the local OSM planet file. |
| `clean_old.sh` | `createCleanOldShScript` | Purge intermediate folders from the previous generation. |
| `generate_online_release.sh` | `createOnlineReleaseShScript` | `update_planet` → `lomaps --mode online --release` (publishes PMTiles to S3). |
| `generate_offline_release.sh` | `createOfflineReleaseShScript` | `update_planet` → `lomaps --mode offline --release` (uploads to Locus Store). |
| `generate_offline_release_DEV.sh` | `createOfflineReleaseDevShScript` | Offline generation against the **DEV** environment. See section 4. |

Build the jar plus every script:

```bash
./gradlew :osmToolsBasic:buildWithAllShScripts
```

Or just what you need — `buildWithPlanetUpdateShScript`, `buildWithOnlineReleaseShScript`,
`buildWithOfflineReleaseShScript`, `buildWithOfflineReleaseDevShScript`. All output lands
in `osmToolsBasic/build/libs/` next to `OsmToolsBasic.jar`.

Deploy `OsmToolsBasic.jar`, the `lib/` directory and the scripts together into the install
directory — the jar's manifest `Class-Path` refers to `lib/*.jar`, so it will not run without
it. Each script resolves the jar relative to its own location, so the directory can live
anywhere as long as `OsmToolsBasic.jar` sits beside the scripts. For the scheduled online
release that directory is `/osm_tools/vectorMaps/`, matching the unit in
[docs/online-generation-timer.md](online-generation-timer.md).

> **Redeploy the scripts, not just the jar.** They carry the `export PATH` for the tool
> directories and the fail-fast tool check; a stale script next to a fresh jar is how a
> release failed on a missing `pmtiles` CLI three hours into the run.

## 2. Command-line arguments

Every release script takes the same arguments:

```bash
./generate_offline_release.sh                  # version = today
./generate_offline_release.sh 2026.07.23       # explicit version (positional)
./generate_offline_release.sh -v 2026.07.23    # explicit version (flag)
./generate_offline_release.sh --help           # full usage, including defaults
./generate_offline_release.sh -s               # reuse the planet file, skip update_planet
```

`--help` prints the resolved defaults for that particular build, so it is the
authoritative reference — the table below is only a summary.

| Option | Available in | Meaning |
|---|---|---|
| `[VERSION]` / `-v, --version VER` | all release scripts | Map version, `yyyy.MM.dd`. Default: today. |
| `-s, --skip-planet-update` | online, offline | Reuse the planet file as it is. |
| `-u, --update-planet` | DEV | Refresh the planet file first (**off** by default). |
| `-r, --release` | DEV | Upload the result to the Locus Store DEV instance (**off** by default). |
| `-h, --help` | all release scripts | Usage and defaults. |

## 3. Environment overrides

Each setting is read from the environment and falls back to a build-time default, so a
single deployed script can be re-pointed without regenerating it:

| Variable | Used by | Default |
|---|---|---|
| `JAVA_OPTS` | all | `-Xmx31g` |
| `CONFIG_FILE` | offline, DEV | `$SCRIPT_DIR/config/config.xml`, DEV: `config_dev.xml` |
| `HGT_DIR` | all release scripts | offline: `$SCRIPT_DIR/hgt/`, online: `/osm_tools/hgt/vectorMaps/hgt/` |
| `STORE_UPLOADER` | offline, DEV | `$SCRIPT_DIR/locusStoreUploader/locusStoreUploader.jar` |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | all | *required* — see below |

> **The S3 keys are required for every subcommand, offline included** — `AppConfig.loadConfig()`
> reads them at startup regardless of mode. The scripts check for them up front and exit with a
> readable message instead of a stack trace. `--help` still works without them.

> `JAVA_OPTS` defaults to `-Xmx31g` deliberately: above 32 GB the JVM turns off compressed
> oops, every object reference widens to 8 bytes, and the batch MBTiles index grows ~25%.
> Raise it only if a run genuinely needs more than 31 GB of live data.

To change a default for good, override it at build time instead of editing the generated file:

```bash
./gradlew :osmToolsBasic:buildWithOfflineReleaseShScript \
    -Plomaps.javaOpts=-Xmx48g \
    -Plomaps.configFile=/etc/lomaps/config.xml
```

Available properties: `lomaps.toolPaths`, `lomaps.javaOpts`, `lomaps.hgtDirOnline`,
`lomaps.hgtDirOffline`, `lomaps.configFile`, `lomaps.configFileDev`, `lomaps.storeUploader`.
Put them in `gradle.properties` to make them permanent for a machine.

## 4. The DEV script

`generate_offline_release_DEV.sh` runs the offline pipeline against the development
environment. It differs from the production offline script in four ways:

1. **`export ENV=DEV`** — picked up by `Utils.isLocalDEV()`, which switches on the local dev
   shortcuts: a reduced bounding box for Mapsforge tiling, no POI V2 database, no Slack
   notifications.
2. **`-e DEV`** — the global `--ls_environment` option, so anything published goes to the
   Locus Store DEV instance rather than production. It is a *global* option and therefore
   sits before the `lomaps` subcommand.
3. **`config_dev.xml`** — a small subset of the map definitions (see `config/config_dev.xml`),
   so a run finishes in minutes. The script checks the file exists before starting and exits
   with a clear message if it does not.
4. **Nothing destructive by default** — neither the planet update nor the store upload runs
   unless asked for.

```bash
./generate_offline_release_DEV.sh                       # generate only, version = today
./generate_offline_release_DEV.sh -u                    # refresh the planet file first
./generate_offline_release_DEV.sh -r                    # upload to the Locus Store DEV instance
./generate_offline_release_DEV.sh 2026.07.23 -u -r      # everything, explicit version
CONFIG_FILE=/path/to/my.xml ./generate_offline_release_DEV.sh   # a different map subset
```

### The DEV map config

`config/config_dev.xml` is a trimmed copy of `config.xml`: the `_world` extract pack (needed
so the continent source extracts exist) plus a few small European countries. The lines are
copied verbatim from the production config, so DEV exercises the same code paths. Add or
remove `<map>` entries as needed — keep the attributes identical to `config.xml`.

## 5. Adding or changing a script

Edit `osmToolsBasic/build.gradle`. A script is declared as a spec passed to
`registerShScriptTask`; the shared header, the `[VERSION] [options]` parsing, the `--help`
text and the credential preflight are rendered by `renderShScript` for all of them:

```groovy
registerShScriptTask('createMyShScript', 'my_script.sh', [
    summary : ['What this script does.'],
    settings: [[name: 'MY_DIR', value: shOpt('myDir', '/default/path'), help: 'Where things live']],
    flags   : [[opts: '-x|--extra', var: 'EXTRA', set: '1', value: '0', help: 'Do the extra thing']],
    banner  : 'My script for version $VERSION',
    run     : [shJava + ' my_subcommand --dir "$MY_DIR"'],
])
```

Pass `parseArgs: false` for a script that takes no arguments, and `requireEnv: []` for one
that does not need the S3 credentials.
